# OBS-007 — Worker + Recovery Surface (tracking milestone)

**Status:** OPEN — requirement earned, contract drafted (Phase 4.11 / AD-053), NOT built.

**Requirement.** Provide a supported operator surface for durable task execution and
stale-work recovery without requiring operators to instantiate runtime/recovery internals
(`run_one` + `RecoveryManager` + a lease threshold).

**Why this is earned.** Repeated operational sessions (OBS-007, then Test Sets #6/#7) showed
the underlying execution/recovery architecture passing while the operator had to hand-wire
the drain loop, recovery duty, and lease threshold. This is the same promotion shape as
OBS-001 (capability exists; ordinary operation requires reproducing internal wiring outside
the supported surface).

**Boundary (what the surface must and must not do):**
- own the drain loop (claim → run → complete/fail) and clean termination (finish in-flight,
  claim no new one);
- own the recovery duty (lease rule, AD-019) with `lease_seconds` as configuration, not a
  per-call operator choice;
- project interrupted state as attempted/unknown — never fabricate a terminal;
- preserve idempotent resumption: `action_id` at-most-once (AD-042), task at-least-once
  (AD-018), weakened by neither;
- add NO authority, NO heartbeat, NO scheduler, NO new execution model, and NO topology
  decision.

**Open decision (deliberately not made here).** Topology — `mnemosyne worker` vs
`mnemosyne run` (a supervisor of serve + workers) vs both — is chosen by further operation,
not by this slice.

**Acceptance bar (the implementation must earn it).** See Phase 4.11 acceptance:
`tests/conformance/test_worker_surface.py` (clean shutdown, crash → attempted/unknown,
recovery generation N+1 with no `action_id` re-execution, terminal `action_id`
reconstruction, new-`action_id` on recovery, and CLI/REST/worker state parity).
